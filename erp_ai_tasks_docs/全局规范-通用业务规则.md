# 全局规范 - 通用业务规则

> 本文档定义ERP系统中跨模块通用的业务规则，包括多租户隔离、软删除、乐观锁、编码生成、审核/反审流程、下推/引入规则、单据流转规则以及单模块开发内部顺序。所有业务模块开发必须严格遵守。

---

## 1. 多租户隔离规则

### 1.1 tenant_id字段要求

- **tenant_id必填**：所有业务表必须包含`tenant_id`字段（bigint类型），不可为空
- **租户标识**：tenant_id标识当前数据所属的租户，是数据隔离的核心字段
- **通用系统字段**：tenant_id属于每张表默认包含的通用系统字段，不重复列出

### 1.2 SQL自动注入

- **MyBatis-Plus多租户插件**：使用`TenantLineInnerInterceptor`自动注入`WHERE tenant_id = ?`条件，所有查询无需手动添加租户过滤
- **联表查询自动注入**：MyBatis-Plus多租户插件对联表查询自动注入tenant_id条件，包括JOIN语句中的关联表
- **插入自动填充**：新增数据时自动取当前登录用户的tenant_id填充到记录中
- **配置位置**：`MybatisPlusConfig.java`中注册TenantLineInnerInterceptor

### 1.3 数据隔离策略

- **索引规范**：tenant_id作为联合索引的首列（如`INDEX(tenant_id, code)`），确保租户隔离查询性能
- **跨租户禁止**：同一查询禁止返回跨租户数据，任何查询场景下都不得绕过tenant_id过滤
- **绕过限制**：仅在极少数全局管理场景下（如平台超级管理员操作）可通过`InterceptorIgnoreHelper`临时忽略多租户插件，必须在使用后立即恢复

### 1.4 租户隔离验证

- 开发阶段必须在SQL日志中确认tenant_id条件已自动注入
- 联表查询需检查每一张关联表是否正确添加了tenant_id条件
- 单元测试和集成测试需覆盖多租户数据隔离场景

## 2. 软删除规则

### 2.1 is_deleted字段要求

- **逻辑删除**：所有业务表删除操作统一使用软删除（`is_deleted = true`），不执行物理DELETE
- **字段定义**：`is_deleted boolean DEFAULT false`，属于通用系统字段，每张业务表默认包含
- **默认值**：新增记录时is_deleted默认为false

### 2.2 @TableLogic注解与MyBatis-Plus插件

- **MyBatis-Plus全局逻辑删除插件**：使用`LogicDeleteInnerInterceptor`自动处理，所有查询自动添加`WHERE is_deleted = false`，无需手动写条件
- **Entity注解**：Entity类的is_deleted字段使用`@TableLogic`注解标注，MyBatis-Plus内置方法自动将DELETE操作转换为UPDATE操作
- **配置位置**：`MybatisPlusConfig.java`中注册LogicDeleteInnerInterceptor

### 2.3 查询自动过滤

- **内置方法自动过滤**：使用MyBatis-Plus内置CRUD方法（selectById/selectList/selectPage等）时，自动过滤已删除数据
- **自定义SQL过滤**：自定义XML映射SQL需手动添加`is_deleted = false`条件，或通过`@InterceptorIgnore`配置自动注入
- **联表查询过滤**：联表查询时，每张关联表都需确保is_deleted = false条件已添加

### 2.4 唯一约束处理

- **部分唯一索引**：涉及唯一性校验的字段（如编码code），采用**部分唯一索引**方式：
  ```sql
  CREATE UNIQUE INDEX uk_xxx_code ON table(code) WHERE is_deleted = false
  ```
- **避免经典陷阱**：仅对未删除数据强制唯一，避免boolean类型is_deleted在联合唯一索引中只能存在一删一活的经典陷阱

### 2.5 恢复操作

- **数据恢复**：软删除数据可通过管理功能恢复（`is_deleted = false`）
- **操作日志**：恢复操作需记录恢复操作日志
- **编码重新生成**：恢复数据时需检查编码唯一性，必要时重新生成编码

## 3. 乐观锁规则

### 3.1 version字段要求

- **字段定义**：所有业务表必须包含`version`字段（int类型），属于通用系统字段
- **默认值**：version默认值为0（或1），每次更新时+1
- **用途**：乐观锁版本号，每次更新+1，防止并发修改冲突
- **从表继承**：从属性质的业务明细子表（如辅助属性子表）**不需要**包含version字段，乐观锁跟随主表

### 3.2 @Version注解与MyBatis-Plus插件

- **Entity注解**：Entity类的version字段使用`@Version`注解标注
- **自动注入**：使用MyBatis-Plus `OptimisticLockerInnerInterceptor`自动注入version条件
- **配置位置**：`MybatisPlusConfig.java`中注册OptimisticLockerInnerInterceptor

### 3.3 并发冲突处理

- **更新时自动检查**：UPDATE语句自动添加`WHERE version = ?`条件，并在更新后自动将version+1
- **冲突检测**：当更新影响的行数为0时，说明数据已被其他用户修改（version不匹配），抛出并发冲突异常
- **前端处理**：并发冲突异常统一返回前端，提示用户"数据已被其他用户修改，请刷新后重试"
- **禁止绕过**：任何业务场景不得绕过乐观锁检查

### 3.4 使用规范

```java
// Entity中version字段注解
@Version
private Integer version;

// Service中更新操作（MyBatis-Plus自动处理version条件）
public void updateOrder(SaleOrder order) {
    int rows = baseMapper.updateById(order);
    if (rows == 0) {
        throw new BusinessException("数据已被其他用户修改，请刷新后重试");
    }
}
```

## 4. 编码生成规则

### 4.1 编码引擎调用方式

- **全局统一**：所有业务单据编号（如SO20250217-0001）和档案编码（如CUST-2025-0001）由编码引擎统一管理
- **前端组件**：前端使用`CodeGenerator`组件（`useCodeRule.ts` Composable）请求编码
- **后端API**：后端提供编码生成API和编码预览API
- **运行时流程**：用户点击"新增"→ 前端请求编码 → 后端生成编码 → 前端填充到编码字段

### 4.2 rule_code绑定

- **规则编码绑定**：每个业务单据的order_no字段或档案的code字段，必须绑定对应的`rule_code`
- **rule_code定义**：在`sys_code_rule`表中配置，如SALE_ORDER、CRM_CUSTOMER、PUR_ORDER等
- **绑定配置**：字段配置界面中，order_no/code类字段从sys_code_rule中选择关联的编码规则rule_code
- **典型rule_code清单**：

| 业务对象 | rule_code | 编码示例 | 段组合 |
|---------|-----------|---------|--------|
| 销售订单 | SALE_ORDER | SO-2025-0001 | 前缀(SO) + 日期(YYYY) + 序号(4位,按年重置) |
| 采购订单 | PUR_ORDER | PO-202502-00001 | 前缀(PO) + 日期(YYYYMM) + 序号(5位,按月重置) |
| 销售出库 | SALE_OUTBOUND | XSCK20250217-001 | 前缀(XSCK) + 日期(YYYYMMDD) + 序号(3位,按日重置) |
| 客户编码 | CRM_CUSTOMER | CUST-0001 | 前缀(CUST) + 序号(4位,不重置) |
| 供应商编码 | SRM_SUPPLIER | SRM-0001 | 前缀(SRM) + 序号(4位,不重置) |
| 商品编码 | PROD_PRODUCT | BJ-RAW-0001 | 组织段(company_code前2位) + 分类段(class_code前3位) + 序号(4位,不重置) |

### 4.3 Redis原子递增与序号生成

- **序号生成器**：使用Redis INCR分布式自增，按重置周期设计key（如`code:seq:{ruleId}:{groupKey}`）
- **并发安全**：Redis INCR保证原子性，高并发下序号不重复
- **数据库行级锁兜底**：同时维护`sys_code_sequence`表（数据库行级锁SELECT ... FOR UPDATE），确保Redis不可用时序号生成不中断
- **重置周期**：支持按年/按月/按日/不重置，重置时序号归零重新开始
- **唯一约束**：`sys_code_sequence`表有UNIQUE(tenant_id, rule_id, group_key)约束
- **编码回退规则**：删除单据不回退序号，已消耗的序号永久占用

### 4.4 三级开关控制

| 优先级 | 开关级别 | 配置位置 | 说明 |
|--------|---------|---------|------|
| 1（最高） | 全局总开关 | 系统参数 system.auto_code_enabled | false时所有编码均手工输入，忽略下级配置 |
| 2 | 规则级开关 | sys_code_rule.is_enabled | 每条编码规则独立控制是否启用自动生成 |
| 3 | 规则级手工权限 | sys_code_rule.allow_manual | 规则启用时，控制用户是否可手工修改自动生成的编码 |

**判定流程**：auto_code_enabled=false → 全部手工 → 否则检查 is_enabled → false则手工 → true则自动生成 → 再看allow_manual决定是否可修改

### 4.5 编码段式结构

编码由若干**段（Segment）**顺序组合而成：

| 段类型 | 说明 | 配置项 |
|--------|------|--------|
| 固定前缀 | 固定字符串 | fixed_value |
| 日期段 | 当前日期格式化 | date_format (YYYY/YYYYMM/YYYYMMDD等) |
| 序号段 | 自增序号 | seq_digits/seq_start/seq_step |
| 组织段 | 当前用户组织字段截取 | source_field/source_truncate |
| 分类段 | 表单分类字段截取 | source_field/source_truncate |
| 自定义段 | 用户自定义值 | default_value |

## 5. 审核/反审流程规则

### 5.1 状态机定义

单据状态由后端状态机控制，前端仅做展示和触发，**禁止前端直接修改status值**。

| 状态值 | 状态名称 | 允许操作 |
|--------|---------|---------|
| 0 | 草稿 | 编辑、删除、提交审核 |
| 1 | 待审核 | 撤回 |
| 2 | 审核中 | -（审批流程流转中） |
| 3 | 已审核 | 反审（需权限）、下推 |
| 4 | 已关闭 | - |
| 5 | 已作废 | 撤销作废 |

### 5.2 审核操作规则

- **审核API**：`POST /api/{module}/{resource}/{id}/audit`
- **审核内容**：状态从草稿→已审核 + 审核人/审核时间记录 + 审核意见存储
- **审核权限**：审核操作需要对应单据的审核权限标识
- **审核后字段锁定**：单据审核通过后，指定字段自动锁定为只读，反审后恢复可编辑
- **联动操作**：审核操作需在事务内完成状态变更 + 库存/财务联动（如库存数量更新、凭证生成）

### 5.3 反审操作规则

- **反审API**：`POST /api/{module}/{resource}/{id}/unaudit`
- **反审内容**：状态从已审核→草稿 + 反审人/反审时间 + 审核意见清除
- **下游单据校验**：反审前必须校验下游单据是否已审核，存在已审核的下游单据则不允许反审
- **联动回冲**：反审操作使用独立事务确保冲回原子性（状态回退 + 库存/财务数据回冲）
- **反审权限**：反审操作需要独立的反审权限标识

### 5.4 作废/撤销作废规则

- **作废API**：状态→已作废 + 作废原因记录 + 校验无下游单据关联
- **作废后字段锁定**：单据作废后，全部字段锁定为只读
- **作废拦截**：存在已执行的下游单据时阻止作废
- **撤销作废**：状态→草稿，恢复单据到草稿状态
- **独立事务**：反审核操作使用独立事务确保冲回原子性

### 5.5 审批流程集成

- **参数判断**：`approval.enabled`参数控制是否启用审批流程
  - `=false`：直接审核通过，不进入审批流程
  - `=true`：走审批流程（多级签核）
- **系统参数联动**：`sale.auto_confirm`/`purchase.auto_confirm`等自动确认参数可与审核引擎联动

### 5.6 前端按钮状态联动

- 根据单据状态动态显示审核/反审/作废/撤销作废按钮
- 审核弹窗：审核意见输入 + 确认审核/反审/作废弹窗
- 使用`AuditDialog.vue`通用审核/反审组件
- 使用`VoidDialog.vue`通用作废/撤销作废组件

## 6. 下推/引入规则

### 6.1 下推定义

- **概念**：将当前单据（源单）的关键数据自动带入目标单据，生成上下游关联的业务单据
- **示例**：报价单下推生成销售订单、销售订单下推生成发货通知单
- **API**：`POST /api/{module}/{resource}/push`（下推操作）、`POST /api/{module}/{resource}/introduce`（引入操作）

### 6.2 源单→目标单字段映射

- **映射规则**：在字段配置中定义源单字段→目标单字段的映射关系，支持一对多映射
- **映射配置项**：
  - 该字段是否允许引入单据时自动带入
  - 该字段是否允许下推单据时自动携带
  - 引入/下推时字段映射规则（源单字段→目标单字段，支持一对多映射）
  - 引入/下推时是否允许覆盖已有数据
  - 流转过程中该字段是否禁止修改
- **数量字段映射**：源单数量→目标单数量，支持数量拆分（一张源单可多次下推）

### 6.3 关联追溯

- **下推关系记录**：每次下推操作记录源单与目标单的关联关系，支持双向追溯
- **追溯组件**：使用`DocTraceDialog.vue`通用单据追溯组件，展示上下游树形追溯
- **追溯维度**：上游来源（本单由哪张单据下推而来）+ 下游流向（本单下推生成了哪些单据）

### 6.4 下推前校验规则

- **状态校验**：源单必须处于允许下推的状态（通常为已审核状态）
- **数量校验**：已下推数量不超过源单总数量，计算剩余可下推数量
- **关联校验**：检查源单与目标单的业务逻辑一致性

### 6.5 下推后源单状态更新

- **状态更新**：下推成功后更新源单的已下推数量/状态（部分下推/全部下推）
- **事务一致性**：跨模块下推使用编程式事务，保证源单和目标单数据一致性
- **关联记录写入**：下推成功后写入下推关联记录

### 6.6 反审时关联下推单检查

- **拦截规则**：反审核时必须检查是否存在已下推的下游单据
- **存在下推单**：如果存在已下推的下游单据，则不允许反审，需先处理下游单据
- **回冲逻辑**：单据下推相关的数量一致性检查、反审核回冲、作废拦截均需专项测试覆盖

## 7. 单据流转规则

### 7.1 流转通用功能清单

| 序号 | 通用功能 | 实现方式 | 说明 |
|------|---------|---------|------|
| 1 | 编码自动生成 | 后端API + 前端CodeGenerator组件 | 详见编码生成规则 |
| 2 | 单据引入 | DocImportDialog组件 | 统一弹窗、筛选、引入 |
| 3 | 单据下推 | DocPushDialog组件 | 统一下推、字段映射 |
| 4 | 单据复制 | DocCopyDialog组件 | 整单/选择性复制 |
| 5 | 审核/反审 | AuditDialog组件 | 审核流程+状态变更 |
| 6 | 作废/撤销 | VoidDialog组件 | 作废+撤销作废 |
| 7 | 单据追溯 | DocTraceDialog组件 | 上下游树形追溯 |

### 7.2 引入流程

- **引入弹窗**：源单类型选择Tab + 源单列表 + 明细行勾选表格 + 数量可修改列 + 确认/取消按钮
- **引入逻辑**：源单查询接口调用 + 已引入过滤 + 数量校验 + 自动填充目标单字段映射
- **明细行编辑**：勾选后支持数量修改、行增删等操作

### 7.3 下推流程

- **下推弹窗**：目标单据类型选择 + 自动携带数据预览 + 确认/取消按钮
- **下推逻辑**：目标单字段映射 + 数量拆分 + 下推后源单状态更新
- **数量拆分**：源单数量→目标单数量，可拆分，已下推数量校验，剩余可下推数量计算

### 7.4 复制流程

- **复制弹窗**：源单搜索选择 + 主表数据预览 + 明细行勾选 + 确认/取消按钮
- **复制逻辑**：源单数据读取 + 编码重新生成 + 复制后进入编辑态 + 清除审核状态
- **注意事项**：关联单据不复制，仅复制主表和从表数据

### 7.5 撤销流程

- **撤销作废**：已作废单据可撤销作废，恢复到草稿状态
- **撤销前提**：无下游已执行单据关联
- **操作记录**：撤销作废需记录操作人和操作时间

### 7.6 全局跨模块流转矩阵（核心路径示例）

| 源单据 | 可下推目标单据 | 触发条件/说明 |
|--------|--------------|-------------|
| 报价单 | 销售订单 | 客户确认报价后下推 |
| 销售订单 | 发货通知单 | 标准下推 |
| 销售订单 | 请购单 | 商品为采购件且库存不足 |
| 销售订单 | 采购订单 | 商品为采购件，跳过请购环节 |
| 销售订单 | 生产通知单 | 商品为自产件 |
| 销售订单 | 委外通知单 | 商品为委外件 |
| 发货通知单 | 出库单 | 标准下推 |
| 请购单 | 采购订单 | 标准下推，支持多单合并 |
| 采购订单 | 入库单 | 标准下推 |
| 生产通知单 | 生产领料单 | 标准下推 |
| MRP运算 | 请购单/采购订单/生产通知单/委外通知单 | 按物料属性生成 |

### 7.7 系统参数控制流转方式

部分系统参数可控制单据是否允许直接新建或必须从上游下推：

| 参数键 | 说明 | 效果 |
|--------|------|------|
| inv.auto_stock_out | 销售出库是否允许直接新建 | false时销售出库单必须从发货通知单下推生成 |
| inv.auto_stock_in | 采购入库是否允许直接新建 | false时采购入库单必须从采购订单下推生成 |
| sale.must_quote_before_order | 是否要求先报价后下单 | true时销售订单必须从报价单下推生成 |
| purchase.require_requisition | 采购是否必须先请购 | true时采购订单必须从请购单下推生成 |
| production.require_notice_before_pick | 领料是否必须先有生产通知单 | true时生产领料单必须从生产通知单下推 |

## 8. 单模块开发内部顺序

### 8.1 开发执行核心原则

| 原则 | 说明 |
|------|------|
| 依赖前置 | 被依赖的模块必须先开发，依赖方必须后开发 |
| 先基础后业务 | 先完成框架、数据库、认证、公共组件，再做业务模块 |
| 先底层后上层 | 先完成后端接口/服务层，再完成前端页面/展示层 |
| 先公共后业务 | 先完成通用引擎（编码引擎/审核引擎/流转引擎），再做业务单据 |
| 后端先行 | 每个模块内部，后端（建表→Entity→Mapper→Service→Controller）先于前端（页面→组件→交互） |
| 单任务原子性 | 每个最末级任务为一个最小不可拆分的开发执行单元，AI单次可独立完成 |

### 8.2 九步开发顺序

每个业务模块的开发严格按以下顺序执行：

```
1. 数据库建表（CREATE TABLE + 索引 + 约束）
2. 后端Entity/DTO/VO定义
3. 后端Mapper层（MyBatis-Plus Mapper + XML映射）
4. 后端Service层（业务逻辑 + 校验 + 联动 + 计算）
5. 后端Controller层（RESTful API接口）
6. 后端单元可运行验证（接口可调通）
7. 前端页面路由注册 + 菜单数据配置
8. 前端页面开发（基于页面类型基座组件 + 字段配置渲染）
9. 前后端联调验证
```

### 8.3 各步骤详细说明

#### 步骤1：数据库建表

- 编写CREATE TABLE语句，包含通用系统字段（id/tenant_id/created_at/updated_at/created_by/updated_by/is_deleted/owner_dept_id/owner_id/version）
- 创建索引（唯一索引、联合索引、部分唯一索引）
- 添加约束（非空、默认值、外键约束）
- 使用Flyway管理SQL版本，命名`V{版本号}__{描述}.sql`

#### 步骤2：后端Entity/DTO/VO定义

- **Entity**：`@TableName` + `@TableId` + `@TableField`注解映射数据库表，`@TableLogic`标注is_deleted，`@Version`标注version
- **DTO**：请求参数使用`@Validated` + Jakarta Validation注解校验，区分CreateDTO/UpdateDTO/QueryDTO
- **VO**：列表VO/详情VO，`@JsonFormat`日期格式，字典翻译字段

#### 步骤3：后端Mapper层

- 继承`BaseMapper<T>`，单表CRUD直接使用MyBatis-Plus内置方法
- 复杂查询编写XML映射（resultMap + 主从联合查询SQL + 动态条件）
- 自定义查询方法（分页查询/条件查询/统计查询SQL）

#### 步骤4：后端Service层

- 定义Service接口（`extends IService<T>`）+ 实现类（`extends ServiceImpl<T>`）
- 业务逻辑核心：校验、联动、计算
- 事务注解加在Service方法上（`@Transactional`）
- 业务校验逻辑：唯一性校验 + 状态校验 + 关联数据校验

#### 步骤5：后端Controller层

- `@RestController` + `@RequestMapping`，仅做参数校验与转发，不含业务逻辑
- RESTful风格API设计
- 统一返回结构`R<T>`（code/message/data）
- 权限注解：`@SaCheckPermission("module:action")`

#### 步骤6：后端单元可运行验证

- 接口可调通（Postman/Swagger验证）
- Service层单元测试（覆盖率≥80%）
- 异常场景覆盖

#### 步骤7：前端页面路由注册 + 菜单数据配置

- 配置前端路由（Vue Router）
- 配置菜单数据（sys_menu表或前端路由元数据）
- 权限标识绑定

#### 步骤8：前端页面开发

- 基于页面类型基座组件（P01~P15共15种标准页面布局）
- 字段配置渲染（后端元数据驱动前端动态渲染）
- 表格列配置、录入组件绑定

#### 步骤9：前后端联调验证

- 接口联调（数据正确传递、异常正确处理）
- 页面功能验证（增删改查完整流程）
- 权限验证（按钮级权限控制生效）

### 8.4 事务管理规范

- 单据保存（主表+从表）使用`@Transactional`数据库事务
- 审核操作需在事务内完成状态变更+库存/财务联动
- 编码生成需在事务内完成序号递增（Redis原子操作或数据库行级锁）
- 反审核操作使用独立事务确保冲回原子性（状态回退+库存/财务数据回冲）
- 作废操作需在事务内校验无已执行的下游单据，有则阻止作废
- 跨模块下推使用编程式事务，保证源单和目标单数据一致性
- 批量操作（如MRP运算生成多个通知单）使用分批事务，每批独立提交避免长事务
