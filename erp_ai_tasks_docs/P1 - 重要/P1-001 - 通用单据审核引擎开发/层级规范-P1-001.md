## 1. 模块架构约束

### 1.1 模块定位
通用单据审核/反审/作废/撤销作废引擎，为所有业务单据提供统一的审核状态流转能力，是系统审核体系的核心基础设施。属于引擎层模块（阶段六），为上层所有业务模块提供标准化的审核服务。

### 1.2 依赖关系
- 前置依赖：P0-001（后端框架）、P0-002（前端框架）、P0-003（数据库）、P0-004（认证与权限）、P0-005（公共组件含审核组件）
- 后续依赖：P1-002（审批流程）、P1-004（流转引擎）、P1-005~P1-015（所有业务模块的单据审核）

### 1.3 技术约束
- 技术栈：Spring Boot + MyBatis-Plus + PostgreSQL，审核状态变更使用行级锁（SELECT ... FOR UPDATE）
- 性能约束：审核操作响应时间 < 500ms；Redis分布式锁TTL=10秒，Key格式 `audit:lock:{docType}:{docId}`
- 安全约束：审核记录（sys_audit_log）不可修改或删除，作为审计追溯依据；审核人与提交人不能为同一人；各操作需独立权限校验（AP-001~AP-006）

## 2. 数据模型关系

### 2.1 核心数据表
| 表名 | 说明 | 关键字段 |
|------|------|---------|
| sys_audit_config | 审核配置表 | id, doc_type, is_audit_enabled, auto_confirm, approval_enabled, audit_timeout_hours, allow_void, void_check_downstream |
| sys_audit_log | 审核日志表 | id, doc_type, doc_id, doc_no, operation_type, from_status, to_status, operator_id, operate_time, opinion |
| sys_audit_status_config | 审核状态配置表 | id, doc_type, status_code, status_name, status_color, allowed_operations(JSON), next_statuses(JSON) |
| sys_param | 系统参数表（复用P0-005） | approval.enabled, sale.auto_confirm, purchase.auto_confirm 等审核相关参数 |

### 2.2 表关系图
- sys_audit_config 为主配置表，按 doc_type 与 sys_audit_status_config 一对多关联，定义每种单据类型的可用状态和流转规则
- sys_audit_log 通过 doc_type + doc_id 与任意业务单据表多态关联，记录该单据的全部审核操作日志
- sys_audit_status_config 中 next_statuses(JSON) 和 allowed_operations(JSON) 定义状态流转矩阵

### 2.3 数据流转
1. 业务单据创建 → 查询 sys_audit_config 获取该单据类型审核配置
2. 提交审核 → 检查 approval_enabled → =false直接已审核(2)，=true → 待审核(1) → 写入 sys_audit_log
3. 审核操作 → 查询 sys_audit_status_config 校验流转合法性 → 更新单据状态 → 写入 sys_audit_log
4. 反审/作废 → 校验下游单据约束（void_check_downstream）→ 状态回退 → 写入 sys_audit_log

## 3. 业务流程

### 3.1 核心业务流程
1. 业务单据创建后处于草稿(0)状态
2. 提交审核：草稿(0)/已驳回(3) → 根据 approval_enabled 判断直接通过或进入待审核(1)
3. 审核通过：待审核(1) → 已审核(2)，触发下游自动操作（如自动下推）
4. 审核驳回：待审核(1) → 已驳回(3)/草稿(0)，驳回原因必填
5. 撤回提交：待审核(1) → 草稿(0)，校验操作人为提交人
6. 反审：已审核(2) → 草稿(0)，校验无已审核下游单据
7. 作废：已审核(2) → 已作废(4)，校验无下游单据关联
8. 撤销作废：已作废(4) → 草稿(0)

### 3.2 业务规则
- 审核引擎与审批流程集成：approval.enabled=false 直接审核通过，=true 走审批流程（P1-002）
- 自动确认参数（如 sale.auto_confirm）仅对新单据生效，不影响已有单据
- 反审前须校验下游关联单据状态，存在已审核下游单据则阻止反审
- 作废后单据数据保留但标记为已作废，不参与业务流转
- 并发控制：PostgreSQL行级锁 + Redis分布式锁双重保障

### 3.3 状态流转
```
草稿(0) → 待审核(1) → 已审核(2) → 已作废(4)
   ↑            ↓              ↓            ↓
   ← 撤回/反审 ← 驳回(3)      → 作废       → 撤销作废
```

状态流转矩阵：
| 当前\目标 | 草稿(0) | 待审核(1) | 已审核(2) | 已驳回(3) | 已作废(4) |
|----------|:---:|:---:|:---:|:---:|:---:|
| 草稿(0) | - | 提交审核 | 自动确认 | - | - |
| 待审核(1) | 撤回 | - | 审核通过 | 审核驳回 | - |
| 已审核(2) | 反审 | - | - | - | 作废 |
| 已驳回(3) | - | 重新提交 | - | - | - |
| 已作废(4) | 撤销作废 | - | - | - | - |

## 4. 接口契约

### 4.1 对外接口
| 接口路径 | 方法 | 说明 |
|---------|------|------|
| /api/engine/audit/submit | POST | 提交审核（草稿/已驳回→待审核/已审核） |
| /api/engine/audit/approve | POST | 审核通过（待审核→已审核+记录审核人/时间/意见） |
| /api/engine/audit/reject | POST | 审核驳回（待审核→已驳回/草稿+驳回原因必填） |
| /api/engine/audit/void | POST | 作废（已审核→已作废+校验无下游单据） |
| /api/engine/audit/cancel-void | POST | 撤销作废（已作废→草稿） |
| /api/engine/audit/withdraw | POST | 撤回提交（待审核→草稿+校验操作人为提交人） |
| /api/engine/audit/log | GET | 查询指定单据全部审核操作日志 |

### 4.2 依赖接口
- P0-004 认证与权限：获取当前操作人信息、校验审核权限（AP-001~AP-006）
- P0-005 公共组件：编码生成服务、系统参数查询
- P1-002 审批流程（可选）：approval.enabled=true 时触发审批实例创建

## 5. 开发顺序约束

### 5.1 必须顺序执行的任务
1. **审核引擎后端开发（P1-001-001）**必须先完成，包含：
   - 审核配置表/状态配置表设计与初始化
   - 核心审核服务（submit/approve/reject/void/cancel-void/withdraw）
   - 审核日志记录机制
   - 并发控制（行级锁+Redis分布式锁）
   - 权限校验集成
2. **审核引擎前端集成（P1-001-002）**依赖后端完成：
   - 审核按钮/弹窗组件开发
   - 审核状态展示与按钮联动

### 5.2 可并行执行的任务
- 审核配置表 CRUD 与审核日志查询可并行开发
- 各业务模块的审核集成（前端组件嵌入）可在后端API稳定后并行实施
- 权限规则配置（AP-001~AP-006）与核心审核逻辑可并行开发
