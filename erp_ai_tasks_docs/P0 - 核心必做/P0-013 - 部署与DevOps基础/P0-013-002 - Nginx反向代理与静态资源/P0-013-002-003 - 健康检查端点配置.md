### 5.1 健康检查端点层级

配置三层健康检查端点，满足不同场景：

1. **轻量级健康检查**（`/health`）：Nginx自身存活，不依赖上游
2. **应用健康检查**（`/actuator/health`）：代理到backend，含数据库/Redis连接状态
3. **就绪探针**（`/ready`）：应用完全就绪，可接受流量（用于K8s readinessProbe）

### 5.2 轻量级健康检查（Nginx层）

```nginx
# /health 直接返回200，不依赖上游服务
location = /health {
    access_log off;
    add_header Content-Type text/plain;
    return 200 "OK\n";
}

# /nginx-health 用于负载均衡器检测Nginx存活
location = /nginx-health {
    access_log off;
    add_header Content-Type text/plain;
    return 200 "NGINX OK\n";
}
```

用途：
- 负载均衡器（如AWS ALB、K8s Ingress Controller）探测Nginx是否存活
- Docker容器HEALTHCHECK
- 不依赖任何上游服务，Nginx启动即可返回200

### 5.3 应用健康检查（代理到backend）

```nginx
# /actuator/health 代理到backend的Spring Boot Actuator端点
location = /actuator/health {
    proxy_pass http://backend/actuator/health;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;

    # 健康检查不应记录访问日志
    access_log off;

    # 超时设置较短，避免阻塞
    proxy_connect_timeout 5s;
    proxy_read_timeout 10s;

    # 健康检查返回非200时标记上游不可用
    proxy_next_upstream error timeout http_502 http_503 http_504;
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 10s;
}
```

响应示例（由backend Spring Boot Actuator提供）：

```json
{
  "status": "UP",
  "components": {
    "db": { "status": "UP", "details": { "database": "PostgreSQL" } },
    "redis": { "status": "UP" },
    "diskSpace": { "status": "UP" }
  }
}
```

### 5.4 故障转移upstream配置

```nginx
upstream backend {
    # 主节点
    server backend-1:8080 max_fails=3 fail_timeout=30s;
    # 备用节点
    server backend-2:8080 max_fails=3 fail_timeout=30s backup;

    keepalive 32;
}

# 在location中启用故障转移
location /api/ {
    proxy_pass http://backend;

    # 触发故障转移的条件
    proxy_next_upstream error timeout http_502 http_503 http_504;
    proxy_next_upstream_tries 3;
    proxy_next_upstream_timeout 30s;

    # 连接与响应超时
    proxy_connect_timeout 10s;
    proxy_send_timeout 30s;
    proxy_read_timeout 60s;
}
```

参数说明：
- `max_fails=3`：连续失败3次后标记为不可用
- `fail_timeout=30s`：30秒内失败次数计数，30秒后重试
- `backup`：备用节点，主节点都不可用时才启用
- `proxy_next_upstream`：触发故障转移的错误类型
- `proxy_next_upstream_tries 3`：最多尝试3个上游节点
- `proxy_next_upstream_timeout 30s`：总故障转移超时时间

### 5.5 主动健康检查（Nginx Plus或第三方模块）

社区版Nginx不支持主动健康检查，需通过以下方式实现：

1. **被动健康检查**（默认）：通过实际请求发现上游故障
2. **Nginx Plus**：内置主动健康检查（商业版本）
   ```nginx
   upstream backend {
       server backend-1:8080;
       health_check interval=5s fails=3 passes=2 uri=/actuator/health;
   }
   ```
3. **开源替代方案**：
   - `nginx_upstream_check_module`（淘宝开源）
   - 配合Consul/etcd做服务发现
   - 使用HAProxy/Envoy替代Nginx做L7负载均衡

本项目使用被动健康检查 + `proxy_next_upstream`，满足基本需求。

### 5.6 健康检查脚本

编写 `scripts/healthcheck.sh` 用于CI/CD或运维监控：

```bash
#!/bin/bash
HEALTH_URL="${HEALTH_URL:-http://localhost/actuator/health}"
MAX_RETRIES=30
INTERVAL=2

for i in $(seq 1 $MAX_RETRIES); do
    STATUS=$(curl -s -o /dev/null -w "%{http_code}" $HEALTH_URL)
    if [ "$STATUS" = "200" ]; then
        BODY=$(curl -s $HEALTH_URL)
        if echo "$BODY" | grep -q '"status":"UP"'; then
            echo "[OK] Application is healthy (attempt $i)"
            exit 0
        fi
    fi
    echo "[WARN] Health check failed (attempt $i/$MAX_RETRIES), status=$STATUS"
    sleep $INTERVAL
done

echo "[ERROR] Application failed to become healthy after $MAX_RETRIES attempts"
exit 1
```

### 5.7 验证

1. `curl http://localhost/health` 返回 `OK` + 200
2. `curl http://localhost/actuator/health` 返回 `{"status":"UP"}` + 200
3. 停止backend容器，再次请求 `/actuator/health` 返回502
4. 启动第二个backend实例，验证故障转移生效（请求自动路由到健康实例）
5. `scripts/healthcheck.sh` 执行成功，输出 `[OK]`
6. 在CI/CD中调用健康检查脚本，部署后自动验证

## 八、易错警示

> ⚠️ 健康检查端点必须轻量，不要在 `/health` 中做复杂业务逻辑或数据库查询，否则会拖垮监控系统

> ⚠️ 健康检查必须关闭访问日志（`access_log off;`），否则监控系统每分钟多次请求会产生大量日志

> ⚠️ `proxy_next_upstream` 不要包含 `http_500`（应用错误），否则应用报错会触发故障转移，导致同一请求重复执行（如重复创建订单）

> ⚠️ `fail_timeout` 设置过短会导致上游临时抖动被误判为不可用，设置过长会导致故障发现延迟

> ⚠️ 健康检查端点要限制访问频率或限制IP，避免暴露给公网被滥用（可通过 `allow`/`deny` 指令控制）

> ⚠️ Spring Boot Actuator的 `/actuator/health` 默认只返回 `{"status":"UP"}`，详细组件信息需要配置 `management.endpoint.health.show-details=always`

> ⚠️ 健康检查脚本超时时间要足够长（start-period），Spring Boot启动需要60s+，过早判定失败会导致误回滚

> ⚠️ 被动健康检查无法主动发现上游故障，只能通过实际请求触发，第一笔失败请求会被用户感知；高可用场景要考虑主动健康检查方案
