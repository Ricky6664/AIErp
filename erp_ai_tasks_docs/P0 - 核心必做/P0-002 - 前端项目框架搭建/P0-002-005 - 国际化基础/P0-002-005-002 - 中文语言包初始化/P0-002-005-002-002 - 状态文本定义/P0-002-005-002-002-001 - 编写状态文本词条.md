### 5.1 词条结构设计
status.ts 按业务域分组定义状态码到文本的映射：
```typescript
const status = {
  // 审核状态 - 用于单据审批流程
  audit: {
    pending: '待审核',
    approved: '已审核',
    rejected: '已驳回'
  },
  // 启用状态 - 用于数据启停控制
  enable: {
    enabled: '启用',
    disabled: '禁用'
  },
  // 订单状态 - 用于采购/销售订单全生命周期
  order: {
    draft: '草稿',
    submitted: '已提交',
    confirmed: '已确认',
    completed: '已完成',
    cancelled: '已取消'
  },
  // 付款状态 - 用于财务收付款
  payment: {
    unpaid: '未付款',
    paid: '已付款',
    refunded: '已退款'
  }
}
```

### 5.2 导出与聚合
- 使用`export default status`导出整个状态文本对象
- 在`zh-CN/index.ts`中通过`import status from './status'`引入
- 聚合方式：`{ status: { ...status } }`，组件中通过`$t('status.audit.pending')`访问
- 状态码Key须与后端返回的状态字段值一致（如后端返回`'pending'`则Key为`pending`）

### 5.3 特殊处理
- 状态值与后端枚举/常量值保持严格一致，前后端需对齐状态码定义
- 跨模块状态码冲突处理：如多个模块都有`pending`状态，通过业务域前缀区分（audit.pending vs order.pending）
- 新增业务域时只需在status对象中添加新属性，不需要修改其他文件
- 状态文本不带标点符号，保持简洁（如'待审核'而非'待审核。'）

## 八、易错警示

> ⚠️ 状态码Key必须与后端返回的状态值完全一致（大小写敏感），如后端返回'PENDING'则Key须为'PENDING'而非'pending'

> ⚠️ 审核状态(audit)的pending/approved/rejected不要与订单状态(order)的draft/completed混淆，它们属于不同业务域

> ⚠️ 状态文本词条不要添加颜色/图标等展示逻辑，这些由renderStatusText函数或组件处理

> ⚠️ status.ts只负责export default对象，不要引入i18n实例或调用$t()函数

> ⚠️ Key命名规范：status.{domain}.{code}（如 status.audit.pending），使用点号分隔
