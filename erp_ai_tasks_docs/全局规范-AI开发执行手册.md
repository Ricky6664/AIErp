# 全局规范 - AI开发执行手册

> **适用范围**：本文档面向所有执行ERP开发任务的AI Agent，提供标准化的任务解读与执行流程。
> **文档定位**：指导AI如何正确读取任务文档、定位规范引用、执行开发操作、验证交付质量。

---

## 1. 任务执行标准流程

每次收到开发任务时，AI必须严格按以下流程执行：

```
Step 1: 解读任务 → Step 2: 加载上下文 → Step 3: 执行开发 → Step 4: 验证交付
```

---

## 2. Step 1：解读任务文档

### 2.1 必读物段

收到任务文档后，按以下顺序读取：

| 优先级 | 读什么 | 获取什么 |
|--------|--------|---------|
| 1 | Section 1 任务标识 | 任务编号、所属模块、任务类型 |
| 2 | Section 2 任务目标 | 具体要做什么（一句话概括） |
| 3 | Section 3 前置依赖 | 需要先完成什么、需要什么环境 |
| 4 | Section 4 关联规范 | 需要遵循哪些全局规范文档 |
| 5 | Section 5 详细开发规格 | 具体怎么做（字段、API、逻辑、交互） |
| 6 | Section 6 交付物清单 | 需要产出哪些文件 |
| 7 | Section 7 验收标准 | 如何判断做得对不对 |
| 8 | Section 8 易错警示 | 需要避免什么错误 |

### 2.2 任务类型判定

根据任务名称和文件路径自动判定任务类型：

| 关键词/路径特征 | 任务类型 | 关注重点 |
|--------------|---------|---------|
| DDL / CREATE TABLE / 建表 / 索引 | DDL | 字段定义、约束、索引设计 |
| Entity / DTO / VO / 数据模型 | ENTITY | 字段映射、注解、校验规则 |
| Mapper / XML映射 / DAO | MAPPER | SQL映射、自定义查询 |
| Service / ServiceImpl / 业务校验 | SERVICE | 业务逻辑、事务、校验规则 |
| Controller / API / 接口 | CONTROLLER | 请求/响应结构、权限、文档注解 |
| .vue / 页面 / 列表 / 表单 / 组件 | FRONTEND | 页面结构、组件、交互、样式 |
| Dockerfile / nginx / docker-compose / CI | DEVOPS | 配置内容、环境差异、安全 |
| 配置文件 / 规范文档 / 配置项 | CONFIG | 配置Key、值、环境差异 |

#### 跨任务类型判定

当一个任务同时涉及多个层级的代码变更（如Service + Mapper + Controller同时修改），按以下规则处理：

1. **识别主任务类型**：以任务目标核心变更对象所属类型为主类型（如核心是业务逻辑则主类型为SERVICE）
2. **以主任务类型模板为主框架**：Section 2任务目标和Section 5详细开发规格以主任务类型模板编写
3. **辅任务类型交付物完整列出**：Section 6交付物清单包含所有涉及层级的文件
4. **验收标准全覆盖**：Section 7验收标准逐层验证所有涉及的层级

### 2.3 信息不足时的处理

当任务文档信息不足时，按以下层级查找补充信息：

```
1. 本任务的"模块上下文"区域（Section 5开头）
2. 所属模块的"模块开发指南"（同级目录）
3. 所属模块的"数据表字段定义"（同级目录，如存在）
4. Section 4引用的全局规范文档（erp_ai_tasks_docs/根目录）
5. 模块索引文件（P0/P1/P2目录下的"模块索引.md"）
```

**最终兜底处理**：当以上所有信息源均无法满足开发需求时（如模块开发指南也不完整）：
- 在末端任务文档中标注"**信息不足-需人工补充**"，明确记录缺失项（如缺失哪些字段定义、API路径、业务规则等）
- 跳过该任务，继续执行下一个可完整执行的任务
- 将缺失信息汇总记录，等待人工补充后再回头处理

**绝对禁止**：
- ❌ 查阅erp_ai_tasks_docs目录以外的总文档
- ❌ 假设"根据设计文档确定"并自行猜测
- ❌ 跳过某个Section不读

## 3. Step 2：加载上下文

### 3.1 模块上下文

每份末端任务文档的Section 5开头包含"本任务模块上下文"信息框，提供：

| 信息项 | 用途 |
|--------|------|
| 涉及数据表 | 确定本任务需要操作哪些表 |
| 涉及API | 确定本任务需要实现/调用哪些接口 |
| 业务规则 | 确定本任务需要遵循哪些业务约束 |
| 技术栈 | 确定本任务使用的技术选型和版本 |

### 3.2 全局规范加载策略

根据任务类型，加载对应的全局规范文档：

| 任务类型 | 必须加载 | 按需加载 |
|---------|---------|---------|
| DDL | 数据库规范、项目架构与开发约束 | 安全开发规范 |
| ENTITY | 后端代码规范、数据库规范 | 安全开发规范 |
| MAPPER | 后端代码规范、数据库规范 | - |
| SERVICE | 后端代码规范、项目架构与开发约束 | 通用业务规则、缓存使用规范 |
| CONTROLLER | 后端代码规范、API接口规范 | 安全开发规范、权限体系规范 |
| FRONTEND | 前端代码规范、页面类型定义 | 表格交互规范、标签页与导航规范 |
| DEVOPS | 部署架构规范、项目架构与开发约束 | 安全开发规范 |
| CONFIG | 项目架构与开发约束 | 系统参数配置规范 |

### 3.3 技术栈版本确认

开始编码前，确认以下版本锁定（来源于《全局规范-技术栈版本锁定》）：

| 技术 | 版本 |
|------|------|
| JDK | 17 LTS（不是21，不是11） |
| Spring Boot | 3.4.x |
| MyBatis-Plus | 3.5.5 |
| PostgreSQL | 15+ |
| Redis | 7.x |
| Sa-Token | 1.39.0 |
| Vue | 3.5.x |
| Vite | 6.x |
| TypeScript | 5.x |
| Element Plus | 2.8.x |

## 4. Step 3：执行开发

### 4.1 后端开发执行顺序

对于包含完整CRUD的业务模块，严格按以下顺序执行：

```
1. Entity/DTO/VO 定义（数据模型层）
2. Mapper 接口 + XML（数据访问层）
3. Service 接口 + Impl（业务逻辑层）
4. Controller（接口层）
```

**编译验证**：每完成一个层级的代码后，执行编译验证（后端: `gradle build`; 前端: `pnpm build`），确保增量正确。发现编译错误立即修复，不要累积到所有层级完成后才验证。

每个层次内部的执行顺序：

**Entity层**：
```
1. Entity类 → 2. CreateDTO → 3. UpdateDTO → 4. QueryDTO → 5. ListVO → 6. DetailVO
```

**Mapper层**：
```
1. Mapper接口（继承BaseMapper） → 2. XML映射文件 → 3. 自定义查询方法
```

**Service层**：
```
1. Service接口定义 → 2. ServiceImpl骨架 → 3. CRUD方法实现 → 4. 业务校验逻辑 → 5. 集成调用（编码引擎/审核引擎等）
```

**Controller层**：
```
1. Controller类骨架（@RestController + @RequestMapping） → 2. 各API方法逐一实现
```

### 4.2 前端开发执行顺序

```
1. API定义文件（src/api/{模块名}/{功能名}.ts）
2. 类型定义文件（src/types/{模块名}/{功能名}.d.ts）
3. 组合式函数（src/composables/{模块名}/use{功能名}.ts）
4. 页面Vue文件（src/views/{模块名}/{功能名}List.vue / Form.vue）
5. 路由注册
6. 菜单配置
7. 国际化词条
```

### 4.3 数据库开发执行顺序

```
1. 确认Flyway当前最新版本号
2. 编写DDL迁移脚本（CREATE TABLE + 索引 + 约束 + 注释）
3. 编写回滚脚本（DROP TABLE + DROP INDEX）
4. 验证DDL执行成功
5. 验证回滚脚本可执行
```

### 4.4 编码过程中的必检清单

**每个Java文件创建后检查**：
- [ ] 包名正确（com.erp.module.{模块名}.{层}）
- [ ] import语句无冗余
- [ ] 类名/文件名符合命名规范
- [ ] 关键注解齐全（@Service/@RestController/@Mapper等）
- [ ] 通用字段通过BaseEntity继承
- [ ] tenant_id由框架自动处理，不在业务代码中手动设置

**每个Vue文件创建后检查**：
- [ ] `<script setup lang="ts">`声明
- [ ] 使用Element Plus组件库
- [ ] API调用使用composable封装
- [ ] v-permission权限控制
- [ ] 国际化使用$t()函数，不硬编码中文

## 5. Step 4：验证交付

### 5.1 交付物完整性检查

对照Section 6交付物清单，逐项确认：

| 检查项 | 方法 |
|--------|------|
| 文件已创建 | 确认文件存在于正确路径 |
| 文件内容完整 | 确认文件不是空文件或仅有骨架 |
| 文件内容正确 | 确认内容与Section 5规格一致 |
| 文件命名正确 | 确认文件名符合项目命名规范 |

### 5.2 代码质量检查

| 检查项 | 方法 |
|--------|------|
| 编译通过 | 后端：mvn compile无ERROR；前端：npm run build无error |
| 无硬编码 | 搜索密码、密钥、URL等敏感信息 |
| 规范一致 | 对照Section 4引用的规范文档检查 |
| 异常处理 | 确认业务异常使用BusinessException |
| 事务正确 | @Transactional注解位置和属性正确 |

### 5.3 验收标准逐项验证

对照Section 7验收标准，逐条执行验证并记录结果：

```
| 序号 | 检查项 | 验证方法 | 结果 |
|------|--------|---------|------|
| 1 | xxx | xxx | ✅通过 / ❌未通过(原因) |
| 2 | xxx | xxx | ✅通过 / ❌未通过(原因) |
```

## 6. 常见陷阱与规避

### 6.1 技术版本陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 使用JDK 21 | 项目锁定JDK 17，Dockerfile用temurin-17 |
| 使用Spring Boot 2.x | 项目使用Spring Boot 3.4.x，Jakarta EE命名空间 |
| 使用Spring Security | 项目使用Sa-Token 1.39.0 |
| 使用MySQL语法 | 项目使用PostgreSQL 15+，注意语法差异 |
| Date类型 | 使用LocalDateTime / LocalDate |

### 6.2 数据库陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 物理DELETE | 使用逻辑删除（is_deleted=true） |
| 唯一索引不加is_deleted条件 | 部分唯一索引：WHERE is_deleted = false |
| 金额用float/double | 统一使用decimal(18,8) |
| 自增主键 | 使用雪花算法（ASSIGN_ID） |
| 缺少通用字段 | 10个通用必含字段全部通过BaseEntity继承 |

### 6.3 业务逻辑陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 手动设置tenant_id | 由MyBatis-Plus多租户插件自动注入 |
| 手动设置created_by/updated_by | 由MetaObjectHandler自动填充 |
| 前端直接修改status | status由后端状态机控制 |
| 删除前不检查关联 | 删除前必须检查子表和引用关系 |
| 编码手动输入 | 由编码引擎自动生成（除非allow_manual=true） |

### 6.4 前端陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 直接调用axios | 使用useApi composable |
| 硬编码中文文本 | 使用$t()国际化函数 |
| 忘记权限控制 | 操作按钮使用v-permission指令 |
| 不使用页面类型基座 | 根据页面类型(P01-P15)选择对应基座组件 |
| 表格不用VxeTable | 大数据量表格使用VxeTable 4.x |

## 7. 异常场景处理

### 7.1 任务文档信息不完整时

| 缺失内容 | 处理方式 |
|---------|---------|
| 字段定义缺失 | 查阅模块开发指南的数据表清单；仍缺失则查阅全局规范-数据库规范的通用字段规则推导 |
| API路径缺失 | 查阅模块开发指南的API接口清单 |
| 业务规则缺失 | 查阅模块开发指南的业务规则区域；仍缺失则查阅全局规范-通用业务规则 |
| 页面规格缺失 | 查阅模块开发指南的页面清单确定页面类型，再查阅全局规范-页面类型定义 |

### 7.2 发现任务文档有错误时

| 错误类型 | 处理方式 |
|---------|---------|
| JDK版本不一致 | 以全局规范-技术栈版本锁定为准（JDK 17） |
| 字段名拼写错误 | 以模块开发指南的数据表清单为准 |
| API路径不一致 | 以模块开发指南的API接口清单为准 |
| 模板套用错误 | 忽略错误的模板内容，根据任务类型和模块上下文推导正确规格 |

### 7.3 任务范围模糊时

| 情况 | 处理方式 |
|------|---------|
| 任务粒度过大 | 拆分为子步骤逐一执行，每步独立交付 |
| 任务与父任务重叠 | 以本任务的Section 5详细规格为准 |
| 跨模块依赖不明确 | 查阅模块开发指南的依赖关系图 |

## 8. 文件输出规范

### 8.1 代码文件编码

- 所有文件使用UTF-8编码
- Java文件不使用BOM
- Vue/TS文件不使用BOM
- SQL文件使用UTF-8无BOM

### 8.2 代码注释规范

**Java文件**：
```java
/**
 * {类说明}
 * 
 * @author AI
 * @since 2026-05-26
 */
```

**Vue文件**：
```vue
<!--
  {页面说明}
  页面类型: P{xx} - {类型名称}
  所属模块: {模块名称}
-->
```

**SQL文件**：
```sql
-- ============================================================
-- {脚本说明}
-- 模块: {模块名称}
-- 作者: AI
-- 日期: 2026-05-26
-- ============================================================
```

## 9. 质量红线

以下问题为质量红线，出现任何一项即判定任务不合格：

| 红线 | 说明 |
|------|------|
| 编译失败 | 代码无法通过编译 |
| 安全漏洞 | 硬编码密码/SQL注入/XSS漏洞 |
| 数据泄露 | 缺少tenant_id隔离/越权访问 |
| 数据丢失 | 使用物理DELETE而非逻辑删除 |
| 事务缺失 | 涉及多表写操作未加@Transactional |
| 权限缺失 | API接口未添加@SaCheckPermission权限注解 |
| 规范违反 | 与Section 4引用的全局规范明显冲突 |
