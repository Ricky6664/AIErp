## Bug #1 — `isCurrentUserSuperadmin` 变量命名误导

**严重程度**：低
**文件**：`erp-ai-web/src/views/system/user/UserRoleDialog.vue`
**位置**：第 115-120 行

### 问题描述

`isCurrentUserSuperadmin` 变量名暗示检查"当前登录用户"是否为超管，但实际逻辑检查的是"被编辑的目标用户"是否已拥有超管角色：

```typescript
const isCurrentUserSuperadmin = computed(() => {
  return initialRoleIds.value.some((id) => {
    const role = roleList.value.find((r) => r.id === id)
    return role?.roleCode === 'superadmin'
  })
})
```

`initialRoleIds` 来源于目标用户的已有角色，而非当前登录用户。该命名会在代码维护时造成混淆。

### 修复方案

重命名为 `isTargetUserSuperadmin`：

```typescript
const isTargetUserSuperadmin = computed(() => {
  return initialRoleIds.value.some((id) => {
    const role = roleList.value.find((r) => r.id === id)
    return role?.roleCode === 'superadmin'
  })
})
```

同时更新模板中的引用 `isCurrentUserSuperadmin` → `isTargetUserSuperadmin`。

## Bug #2 — `fetchUserRoles` 使用角色名称匹配角色 ID，方式脆弱

**严重程度**：中
**文件**：`erp-ai-web/src/views/system/user/UserRoleDialog.vue`
**位置**：`fetchUserRoles` 函数（第 161-175 行）

### 问题描述

当前逻辑通过角色名称匹配获取角色 ID：

```typescript
async function fetchUserRoles(): Promise<void> {
  if (!props.userId) return
  try {
    const user = (await getUserDetail(props.userId)) as unknown as Record<string, unknown>
    const roleNames = (user.roleNames as string[]) ?? []
    const ids = roleNames
      .map((name) => roleList.value.find((r) => r.roleName === name)?.id)
      .filter((id): id is number => id !== undefined)
    selectedRoleIds.value = [...ids]
    initialRoleIds.value = [...ids]
  } catch { ... }
}
```

**问题**：
1. 角色名称作为匹配键不可靠（名称可能重复、变更、含特殊字符）
2. 使用 `as unknown as Record<string, unknown>` 绕过类型检查，`roleNames` 字段不在 `UserListItem` 类型定义中
3. 若 `getUserDetail` 返回的角色列表中某个角色不在 `roleList` 中，该角色将被静默丢失

### 修复方案

**方案 A（推荐）**：要求后端 `getUserDetail` API 直接返回 `roleIds: number[]`，前端直接用 ID 数组：

```typescript
async function fetchUserRoles(): Promise<void> {
  if (!props.userId) return
  try {
    const user = (await getUserDetail(props.userId)) as { roleIds?: number[] }
    const ids = user.roleIds ?? []
    selectedRoleIds.value = [...ids]
    initialRoleIds.value = [...ids]
  } catch {
    selectedRoleIds.value = []
    initialRoleIds.value = []
  }
}
```

同时更新 `UserListItem` 类型定义：
```typescript
export interface UserListItem {
  // ...existing fields...
  roleIds?: number[]
}
```

**方案 B（临时）**：如果后端暂时无法修改，在匹配失败时记录警告：
```typescript
const ids: number[] = []
for (const name of roleNames) {
  const role = roleList.value.find((r) => r.roleName === name)
  if (role) {
    ids.push(role.id)
  } else {
    console.warn(`Role "${name}" not found in role list`)
  }
}
```

## 改进建议

### Warn #1 — `fetchExclusions` 存在 N+1 API 调用问题

**文件**：`UserRoleDialog.vue:177-186`
**说明**：`fetchExclusions` 对每个角色单独调用 `getRoleExclusions(role.id)`。若系统有 50 个角色，每次打开弹窗产生 50 次 HTTP 请求。虽然使用了 `Promise.allSettled` 并发执行，但仍会对服务端造成不必要的压力。
**建议**：新增后端批量查询接口 `POST /api/system/role/exclusion/batch`（接收 `roleIds: number[]`，返回 `Map<roleId, number[]>`），前端只需 1 次请求即可获取全部互斥关系。

### Warn #2 — `selectAll` 未检查角色互斥

**文件**：`UserRoleDialog.vue:188-192`
**说明**：点击"全选"按钮会选中所有角色（超管除外），可能立即产生互斥冲突。用户看到大量红色警告会感到困惑。
**建议**：在全选时自动排除互斥角色，或全选后弹出提示告知用户存在互斥需手动调整。

### Warn #3 — `handleSave` 的 catch 块为空

**文件**：`UserRoleDialog.vue:220-221`
**说明**：保存失败时 catch 块完全为空，依赖请求拦截器显示错误消息。如果拦截器未覆盖此场景（如网络超时无响应体），用户将看不到任何错误反馈。
**建议**：添加兜底错误提示：
```typescript
} catch {
  ElMessage.error('角色分配失败，请稍后重试')
}
```

### Warn #4 — `handleSave` 未检查空角色分配

**文件**：`UserRoleDialog.vue:198-225`
**说明**：允许将用户角色清空（selectedRoleIds 为空数组），这在某些业务场景下可能是合法的（如临时禁用用户所有权限），但应给予用户二次确认提示。
**建议**：若 selectedRoleIds 为空，弹出额外确认提示"确定移除该用户的所有角色？该用户将无法访问任何受权限控制的资源。"
